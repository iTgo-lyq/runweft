# 整理需求

把已有信息和项目现状整理成可共同确认的 `requirement.md`。依次建立当前理解、澄清产品问题、完成 Research、写入需求并完成 Review。

## 1. 建立当前理解

读取当前对话、用户指定材料、相关 Specs 和活跃 Changes，再从目标附近搜索 `AGENTS.md`、README、依赖、配置、代码和测试，确认现有行为、术语、边界与约束。按需扩大范围，不遍历无关内容，也不把可以从项目中查明的事实重新问给用户。

区分明确事实、合理推断、调查证据和未决问题。描述用户结果与可观察行为，不提前编写实现方案。

凡读取会话外的资源链接，首次使用时立即在 `requirement.md` 的可选 `## 协作资源` 中记录标题、链接、读取日期，以及影响当前需求的结论梗概，确保后续会话不依赖聊天记录恢复上下文。调查详情较多时写入 `research.md`，但 Requirement 仍保留入口和摘要。外部材料只作为需求输入；区分材料陈述、AI 推断和项目决策，与 Specs、实现或已确认 Requirement 冲突时显式提出，不静默覆盖。

由当前 Change 生成的外部文档也记录在 `## 协作资源`，注明链接、用途、目标读者和同步状态。只在实际存在协作资源时添加该章节，例如：

```markdown
## 协作资源

### 输入

- [<标题>](<链接>)（读取 YYYY-MM-DD）：<影响本次需求的结论梗概>

### 输出

- [<文档标题>](<链接>)：<用途>；读者：<目标读者>；同步状态：<与当前 Requirement 一致 / 待确认是否同步>
```

## 2. 澄清与 Research

Research 负责主动探索项目内外可获得的证据，并对证据足够的内容作可靠推理。技术澄清不是第二轮 Research；只有同时满足以下条件的未知项才移交技术澄清：

1. 无法通过代码、配置、Specs、依赖、官方资料、只读外部状态或必要实验主动发现；
2. 无法根据已有证据可靠推理；
3. 技术实现必须依赖其明确结果。

只追问会改变目标、范围、核心行为或验收方式的问题；每轮根据新信息继续收敛：

- 需要用户取舍：直接询问；
- 可以可靠推断：标记为当前假设；
- 暂不影响 Review：记录为未决问题并说明影响；
- 只影响实现但可调查或可推理：在 Research 中解决；满足上述三个条件：留给技术澄清。

项目内只读搜索属于需求整理。沿实现链路调查与当前 Change 相关的代码入口、依赖版本、环境配置、安全接入和外部依赖；发现证据缺口时继续查找，不因其属于技术内容就推迟。可合理推理的实现判断需标明依据和假设，不转问用户。

以下内容可以进入技术澄清：仓库与可访问环境均未声明的第三方服务、未建立的接口或数据契约、数据库凭证的交付与注入约定，以及只有责任人能够给出的资源标识、授权状态或完成信号。不得把密码、Token、连接串等秘密值写入文档。

安装依赖、产生持久文件、运行成本较高的实验或访问外部状态前，先说明目的与影响，必要时取得用户确认。结论使用“已确认”“有条件可行”“尚未验证”或“当前受阻”；内容较多且后续仍需引用时写入 `research.md`，Requirement 只保留影响目标、范围、行为或验收的结论。

## 3. 写入 Requirement

- 未来行为写入 `changes/<change-slug>/requirement.md`，继续已有目标时更新原 Change；
- 修正当前实现的错误描述或补录既有行为时，直接更新对应 Spec；
- 把目标行为按 `ADDED`、`MODIFIED`、`REMOVED` 写入 `## 行为变化`，每项标明 `<capability-path>` 和行为名称；
- 按项目文档规则标记规模，让用户在确认需求时一并确认；Plan 后仍可向上校准；
- 不加入任务清单、预计修改文件或大段调查过程；
- 省略空章节，不使用固定篇幅或质量评分。

只保留非空的变化分类；不改变可观察行为时在 `## 行为变化` 下写“无”。

- `ADDED`：当前不存在的新 capability 或可观察行为，写清目标行为。
- `MODIFIED`：已有行为的条件、结果或约束改变，分别写清“当前”和“目标”。
- `REMOVED`：已有行为不再有效，写清删除对象；存在替代方式或迁移影响时一并说明。

### 小型模板

```markdown
# <需求名称>

> 状态：草稿
> 规模：小型
> 更新：YYYY-MM-DD

## 需求

<一句话描述目标和可观察结果。>

## 行为变化

### ADDED / MODIFIED / REMOVED

- `<capability-path>` — <行为名称>：<按分类要求描述>

## 验收

- [ ] <可明确判断完成的结果>
```

### 中型与大型模板

```markdown
# <需求名称>

> 状态：草稿
> 规模：中型 / 大型
> 更新：YYYY-MM-DD

## Review 导读

- **目标：** <用户最终获得的变化>
- **待确认：** <最影响方向的目标、范围或行为>
- **当前假设：** <可能改变范围或行为的未确认判断>
- **可行性：** <仅在调查结论影响需求时写一句状态和限制>

## 背景与目标

<当前问题、受影响的人和期望结果。>

## 范围

### 包含

- <必须覆盖的能力或场景>

### 不包含

- <容易被误认为属于本次、但明确不做的内容>

## 行为变化

### ADDED

#### `<capability-path>`：<行为名称>

<新增的目标行为。>

### MODIFIED

#### `<capability-path>`：<行为名称>

- 当前：<已验证的当前行为>
- 目标：<修改后的完整行为>

### REMOVED

#### `<capability-path>`：<行为名称>

<不再有效的行为，以及必要的替代方式或迁移影响。>

## 验收标准

- [ ] <可通过测试、演示或观察明确判断的结果>

## 约束与依赖

- <真正限制需求空间的事实>

## 可行性与限制

- 状态：<已确认 / 有条件可行 / 尚未验证 / 当前受阻>
- 结论：<与需求判断直接相关的结论>
- 条件或限制：<会改变范围、行为或验收的前提>
- 依据：<项目证据或一手资料链接，注明日期>
- 后续验证：<仅在尚未验证时填写>

## 未决问题

- <问题>；影响：<会改变的范围、行为或验收方式>
```

行为变化按用户能力或完整流程组织，不按接口、存储、进程等技术层拆分。只写容易误解的范围边界；验收标准不重复目标行为、不指定实现文件、不凭空发明指标。约束只记录限制需求空间的事实，可行性只在影响需求判断时保留。

## 4. Review 与确认

交付时先说明目标、待确认内容、关键假设、必要限制和未决问题，再引导用户审阅范围、`ADDED`、`MODIFIED`、`REMOVED` 与验收标准。

吸收反馈时，将有效结论合入正文，删除被否定、已解决或过期的提示。用户明确确认 Requirement 后，将状态改为“已确认”并进入技术澄清；不要创建 Plan 或开始实现。
