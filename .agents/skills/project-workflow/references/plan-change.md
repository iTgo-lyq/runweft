# 规划 Change

为每个进入工作流的 Change，将已确认的 `requirement.md` 和 `technical.md` 拆成可持续执行、逐项验证并供人审阅的 `plan.md`。

## 前置条件

- 需求状态为“已确认”或“进行中”。
- Technical 状态为“已确认”。
- 目标行为、实现路径、外部前置条件和验证方式足以支持实施。
- 会改变方案方向的未决问题已经解决；否则回到技术澄清，改变目标行为时回到需求流程。

规划阶段不修改正式交付代码，只更新 Change 文档。读取需求、技术方案、相关 Specs 和项目规则，不重新调研已确认的核心方案。

## 拆解方法

1. 识别实现边界、现有模式、关键风险和依赖关系。
2. 优先拆成端到端的垂直切片，让每个任务交付可独立验证的行为。
3. 让每个任务适合一次聚焦的 Agent 会话；按认知负担和验证边界判断，不使用固定文件数或代码行数。
4. 把高风险或仍需验证的假设放在前面，尽早失败。
5. 只有依赖真正解除后才并行；共享契约先明确，再拆并行任务。
6. 宽范围机械改动无法垂直切片时，使用 expand → migrate → contract，保持中间状态可运行。

如果需求和现有实现之间存在明显前置重构，先安排使后续改动更容易的最小重构任务，不顺手扩大范围。

如果交付包含根据 Requirement 或 Plan 创建、更新外部文档，必须设置明确任务，写清内容来源、用途、目标读者，以及复用已有文档还是新建。先检查 Requirement 的“协作资源”，已有同用途输出时默认更新原文档，不重复生成。

拆解后按流程矩阵重新校准规模并同步 Requirement。所有任务独立创建本地 Commit；执行记录按项目文档体系使用 `execution.md`。

## Plan 格式

保存到当前 Change 的 `plan.md`：

```markdown
# <Change 名称>实施计划

> 来源：./requirement.md
> 技术方案：./technical.md
> 状态：待确认
> 执行模式：逐任务提交 / 分步记录并提交

## 交付目标

<完成后用户能获得的结果。>

## 关键决策与风险

- <只记录会影响后续任务的实现决策、约束或风险。>

## 任务

### T1 <任务名称>

- 状态：待开始
- 交付：<本任务完成的端到端结果>
- 依赖：无
- 验收：<可明确判断完成的条件>
- 验证：<聚焦测试、构建、端到端或其他检查>

### T2 <任务名称>

- 状态：待开始
- 交付：<结果>
- 依赖：T1
- 验收：<条件>
- 验证：<检查方式>

## 整体验证

- <覆盖完整需求的最终检查。>
```

Plan 和任务状态使用项目文档定义的值，不另建 TODO、状态或进度文件。

任务编号在 Plan 确认后保持稳定。已提交任务不得重编号或复用编号；新增工作使用新编号。

## Review 边界

AI 基于已确认需求和技术方案生成 Plan 后暂停，向用户说明交付路径、任务依赖和主要风险。仍有方案决策时返回技术澄清，不提交 Plan 确认。用户确认整体 Plan 后将状态改为“待执行”；不要求逐任务审批。

Plan Review 之后，只有方案需要改变用户行为、引入计划外且难以回退的数据或外部状态变更、扩大权限或新增重要依赖时，才重新请求用户决策。普通任务调整由 AI 在已确认范围内自行维护。

不要把 Plan 写成逐文件操作脚本。文件或模块路径只有在帮助界定边界时才记录，并在执行时重新核实。

Plan 只有在完整覆盖 Requirement、未引入范围外功能，且每个任务的交付、依赖、验收和验证方式足以形成明确可执行前沿时，才可提交确认。
