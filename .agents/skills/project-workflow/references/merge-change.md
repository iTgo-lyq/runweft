# 合并 Change

把活跃 Change 合入、迁回、移植或同步到另一分支或工作区时，先做只读预检。合码是原 Change 的集成步骤，不创建新 Change，也不因目标分支差异改写原追踪文档。

## 何时创建独立方案

只有机械冲突少、两侧行为与契约一致、自动合并后可直接通过原验证时，才能不创建额外文档。

出现任一情况时，在原 Change 目录创建 `merge-technical.md`：

- 冲突跨越多个包、应用、Specs、锁文件、Schema、子仓或共享契约；
- 自动合并后的树仍有消费者断点、构建断点、残留引用或数据语义不一致；
- 主干在 merge base 后实现了会改变接入方式、所有权或验证路径的新能力；
- 工作区方案与主干活跃 Change、已实现行为或公共接口存在取舍；
- 不能通过保留一侧或机械拼接解决，必须决定来源优先级、迁移顺序、兼容、延期项或回退边界。

“大量冲突”不只指 Git 标记的文本冲突。即使只有一处文本冲突，只要自动合并产生跨消费者的语义断点，也必须创建独立方案。

## 文档归属与保护

- 文件固定为原活跃 Change 下的 `merge-technical.md`。
- `requirement.md`、`technical.md`、`plan.md` 和 `execution.md` 继续描述原 Change，不为适配主干重写目标、方案、任务或历史结果。
- 主干其他活跃 Change 的文档只作为输入读取；合码方案阶段不替对方改写追踪状态。
- 合码暴露原 Change 本身的需求或技术缺陷时，停止受影响决策，按原工作流回到对应门禁；不能把产品或架构变化藏进合码文档。
- `merge-technical.md` 不替代 Plan，不创建合码 Plan，不改变原 Change 的规模和状态。

## 只读预检

预检不得执行真实 merge、rebase、cherry-pick 或修改任一工作区。至少核对：

- 主干工作区路径、分支、HEAD、工作区状态和相关活跃 Change；
- 源工作区路径、分支、HEAD、工作区状态和原 Change 状态；
- merge base、两侧提交数、提交清单和路径变更；
- Git 文本冲突、自动合并路径及生成的合并树；
- 合并树中的依赖、import、构建、测试、Schema、锁文件、子仓和文档语义断点。

优先使用 `git merge-base`、`git rev-list`、`git diff --name-status` 和 `git merge-tree --write-tree --name-only --messages`。合并树生成成功不代表方案可合入；必须继续检查语义断点。

主干或源 HEAD 变化后重新预检。工作区存在未提交内容时，明确所有者和影响，不把它计入可重放提交，也不覆盖或顺带修改。

## 文档内容

`merge-technical.md` 必须把主干与源工作区分开描述，不能只列冲突文件：

```markdown
# <Change 名称>合码技术方案

> 来源 Change：./technical.md
> 状态：草稿
> 更新：YYYY-MM-DD

## Review 导读

- **合码目标：** <源 Change 合入哪个目标>
- **来源优先级：** <哪些领域以主干或工作区为准>
- **冲突结论：** <文本冲突与语义断点概况>
- **待确认：** <只有用户才能决定的取舍>

## 合码基线

| 对象 | 工作区 | 分支 | HEAD | 状态 |
| ---- | ------ | ---- | ---- | ---- |
| 主干 | ... | ... | ... | ... |
| 源 Change | ... | ... | ... | ... |

- Merge base：...

## 主干变更

<merge base 后与本次集成相关的实现、契约和活跃 Change。>

## 工作区变更

<原 Change 提交、已确认设计和明确不包含的内容。>

## 冲突与决策

| 路径或能力 | 主干 | 工作区 | 合并决策 | 依据与验证 |
| ---------- | ---- | ------ | -------- | ---------- |
| ... | ... | ... | ... | ... |

## 合并顺序与回退

<检查点、顺序、失败停止条件和回退方式。>

## 验证

<文本冲突、语义断点、构建、测试和残留白名单。>

## 延期项

<明确不处理的断点、所有者和后续入口。>
```

来源优先级必须按领域说明，不得笼统写“以一侧为准”后覆盖另一侧已确认行为。冲突矩阵要覆盖 Git 冲突和自动合并后的语义断点；延期项必须是明确白名单，不能用“后续处理”隐藏未知范围。

## 确认与执行

Research 未完成时状态为“草稿”。方案覆盖两侧事实、冲突决策、顺序、回退和验证后改为“待确认”，在会话中向用户提交具体取舍。用户确认后改为“已确认”，才能执行真实合并。

目标或源 HEAD 变化、冲突集合扩大、来源优先级变化时，立即重新预检并将状态退回“待确认”。纯提交号前进但预检证明方案与冲突集合未变化时，更新基线和证据即可。

合并完成后在文档补充实际目标 HEAD、采用的冲突决策、验证结果和仍延期白名单。原 Change 按其 Plan 和关闭流程继续，不因完成合码自动验收或归档。
