# 执行 Change

在已通过对应人工门禁后实施当前 Change，并让代码、任务状态和需求保持一致。

## 开始前

读取 `requirement.md`、`technical.md`、`plan.md`、存在时的 `execution.md`、相关 Specs、项目规则和当前工作区状态。确认 Requirement、Technical 与 Plan 均已通过门禁，然后将 Requirement 改为“进行中”，将 Plan 改为“执行中”。

开始修改前检查其他活跃 Change 和 Git 工作区，按流程矩阵执行并行限制。

从 Plan 中选择依赖已经完成的任务。多个任务处于可执行前沿时，优先处理风险更高或更能验证整体方向的任务；同一 Change 内也只有实现边界独立时才并行。小型 Change 使用一个紧凑任务即可，不跳过 Plan。

## 单任务循环

Plan 确认后默认由主 Agent 执行。用户或当前环境明确授权委派，且已有可用工具时，才按独立任务委托实现与自检；不依赖仓库之外未安装的委派 skill。用户指定执行方式时遵从用户要求。

委托后，主 Agent 从 `execution.md` 收回结果，负责 Review、验收、任务状态和 Commit。受委托的执行者只完成指定任务并记录摘要，不再次委派或自行推进以下检查点。

1. 将任务状态改为“进行中”，读取完成它所需的最小上下文。
2. 实现使任务交付结果成立的最小完整切片，复用现有模式，避免过早抽象。
3. 运行与改动范围相称的聚焦测试、类型检查、构建和端到端验证。
4. 对照任务验收条件和 Requirement 检查结果，完成下述任务检查点。
5. Commit 成功后再开始下一任务。不要重复运行代码未变化时已经成功的检查。

每个增量保持系统可运行。未完成功能不得意外暴露；必要时使用安全默认值、兼容过渡或项目已有的特性开关。数据库、协议或共享接口迁移优先采用可回退的 expand → migrate → contract。

## 执行中反馈与文档同步

发现已确认文档未覆盖或与实现证据冲突的信息时，不得用默认假设、临时兼容、额外补丁或仅写 `execution.md` 吞掉问题。发现后立即处理，不等当前任务或整个 Change 结束：

- **技术缺口**：停止受影响实现，将任务标记为“已阻塞”；把已验证证据、缺失内容和影响范围写入 `technical.md`，将 Technical 改为“草稿”，并立即向用户说明。可主动探索或可靠推理的缺口返回 Research；只有无法探索、无法推理且实现必需的契约才请求用户输入。取得 Research 结论或用户反馈后立即更新 Technical；方案变化影响任务时同步 Plan，重新通过受影响门禁后解除阻塞。
- **需求变化**：用户在执行中新增、修改或删除目标行为时，停止受影响实现，立即把变化写入 `requirement.md` 的对应分类，并同步范围、验收标准和状态。随后重新执行受影响的 Research，更新 Technical 与 Plan，从最早失效的门禁继续。

用户反馈已经明确确认的内容不重复询问；文档中仍存在新增推断、连带行为或方案选择时，只对这些未确认部分执行门禁。未受影响的任务可以继续，但不得依赖尚未确认的行为或契约。

## 外部文档协作

只有用户明确要求，或已确认 Plan 包含对应任务时，才创建或更新外部文档。执行前按项目文档中的协作资源规则检查已有链接；同一用途已有文档时复用并更新，不另建重复文档。创建后立即把标题、链接、用途、目标读者和同步状态写回“协作资源”。

未明确发布范围时只创建私有草稿；分享、权限调整和通知接收人按用户要求或已确认 Plan 执行。存在外部文档后，Requirement、Technical 或 Plan 变化影响文档内容时，将同步状态标为“待确认是否同步”并询问用户，不默认修改外部文档，也不重新生成一篇。仓库中的 Requirement、Technical、Plan 和 Specs 仍是项目事实来源。

## 维护 Plan

- Plan 是当前执行状态，不是操作日志。只更新任务状态、依赖和会影响后续工作的关键决策。
- 任务拆解不合理但 Requirement 不变时，直接调整 Plan，并保证已完成工作仍可追溯。
- 已提交任务的编号和记录不可重写；新增或修正工作追加新任务。
- Change 执行中不再满足当前规模条件时，按流程矩阵升级并补齐门禁和文档后再继续。
- 实现发现需求行为需要改变时，按“执行中反馈与文档同步”返回需求流程。
- 实现推翻已确认的架构、安全、契约或外部依赖时，按“执行中反馈与文档同步”返回技术澄清。
- 遇到外部阻塞时标记“已阻塞”，写明阻塞条件和解除方式；不要假装完成。

## 任务检查点

每个 Plan 任务必须独立提交，不能积攒或合并：

1. 完成该任务的实现和聚焦验证。
2. 在 Plan 将任务标为“已完成”；存在 `execution.md` 时核验对应记录并补齐 Commit 标题。
3. 只暂存该任务的代码、验证和同步文档；不得带入其他任务或用户改动。
4. 创建一个本地 Commit，标题包含稳定任务编号，例如 `<change-slug> T1: <结果>`。
5. 确认 Commit 成功且任务无遗留；失败时任务保持未完成。

不要记录当前 Commit hash：文档与实现应进入同一个 Commit，hash 在提交前尚不存在。任务编号和唯一标题负责关联，精确 hash 由 Git 历史解析。Commit 或校验失败时任务保持未完成；不要跳过 hooks、混入无关改动或用额外 bookkeeping Commit 修补记录。

## 执行结果记录

按项目文档体系的适用范围使用当前 Change 的 `execution.md`。执行者在交回结果或遇到阻塞时更新当前任务章节，返修覆盖该任务的过时结论，保留其他任务记录。结果写明实际完成范围；验证写明命令、结果和未运行项；未解决事项写明证据与待决策内容，不抄录完整终端日志。

执行者的摘要不代表验收通过。Commit 字段由主 Agent 在 Review 和验证通过后补齐，任务未通过时不填写；需求或技术缺口仍须按“执行中反馈与文档同步”处理。

`execution.md` 使用以下最小格式；可选字段没有内容时省略：

```markdown
# <Change 名称>执行概况

## T1 <任务名称>

- 结果：<完成的可观察结果>
- 验证：<命令或检查及结果>
- 偏差：<相对 Plan 的必要变化；没有则省略>
- 未解决：<未完成项、阻塞证据或待决策事项；没有则省略>
- Commit：`<change-slug> T1: <结果>`
```

## 结束执行

Plan 中所有必要任务都有独立 Commit、适用的执行记录齐全且整体验证通过后，进入关闭流程。人工验收前不得将 Requirement 标记为“已完成”。
