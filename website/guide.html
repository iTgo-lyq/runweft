开始协作

从安装，到第一次委派。

先在本机跑通一条完整路径。之后，你可以选择独立工作区，或让任务去另一台机器执行。

准备好这些

  • macOS 或 glibc Linux，确认机器是 arm64 还是 x64。
  • Git 2.31+，以及已安装并登录的 Codex 或 Claude Code。
  • 在实际项目目录中操作；使用独立 worktree 时，需要已提交的 Git 基线。

Runweft 安装包已包含配套 HAPI，无需另装 Bun 或 Node。使用 Git LFS 的项目，源机器与执行机器还需 Git LFS。

01 / INSTALL

安装，然后启动本地服务。

在下载区明确选择机器平台，下载对应 .tgz。在该文件所在目录运行页面提供的安装命令，命令会先校验 SHA-256，再解包到个人目录。成功后，runweft --version 应输出 {{VERSION}}。

保留解包目录及相邻的 bin/runweft 和 bin/hapi，不要只移动一个程序。Mac 包未签名、未公证；若系统阻止运行，核对校验值后，通过系统“隐私与安全性”设置允许该程序。

让新终端也能找到命令

安装命令中的 export 只对当前终端生效。按你使用的 shell，选择一条配置命令运行一次：

zsh · macOS 常用
printf '\nexport PATH="$HOME/.local/bin:$PATH"\n' >> "$HOME/.zshrc"
bash · Linux 常用
printf '\nexport PATH="$HOME/.local/bin:$PATH"\n' >> "$HOME/.bashrc"

初始化并启动

Terminal
runweft init
runweft start
runweft status
runweft open

本地模式自动管理本机服务和 Runner。默认入口 http://127.0.0.1:3210，数据根 ~/.runweft。open 打开协作看板；无图形环境时，在本机交互终端执行 runweft auth token 取得令牌，再手动打开入口的 /runweft/ 登录。

02 / CONNECT

把 MCP 接入你使用的客户端。

Codex 或 Claude Code 是宿主：你与主 agent 对话、发起委派的地方。先完成原生客户端的模型登录，再安装 Runweft MCP。

全局安装 · 保留其他 MCP 配置
runweft mcp install
runweft mcp check

然后进入项目目录，启动或重新打开原生会话，让主 agent 调用 runweft_status 检查身份、工作区和连接。安装是全局的，不会将工作区锁定到安装时所在目录。

检查连接，不等于完成模型调用。

mcp check 检查配置、握手和服务；机器探测也不验证模型登录。最终以第一条真实任务的结果为准。

每次实际修改会先备份客户端配置；已有模型设置、其他 MCP 和会话保留。可以用 runweft mcp backups 查看备份，或用 runweft mcp uninstall 移除 Runweft 入口。

03 / CONFIGURE

告诉 Runweft：在哪执行，做什么。

这里的 Agent 定义描述一个可委派的职责，与正在和你对话的主 agent 是两件事。引用关系是 Agent → runtime → 机器，宿主与 runtime 可以交叉搭配。

机器在哪执行

已连接的 HAPI Runner 身份。全局登记，跨项目使用。

runtime用什么工具

某台机器上的 Codex 或 Claude Code。与机器分开登记。

Agent承担什么职责

YAML 中的描述和指令。可全局或项目级，绑定 runtime ID。

登记当前机器

确保 runweft start 已成功
runweft machine register --name '我的开发机'

登记一个已安装的执行工具

选择你已完成模型登录的工具
runweft runtime discover
runweft runtime register codex
runweft runtime list

discover 只探测，不会创建登记。复制 runtime register 返回的完整 runtime ID，也可以从 runtime list 找到它，下一步绑定时会用到。

创建 reviewer，并写下它的职责

默认创建全局 Agent 定义
runweft agent init reviewer
runweft agent show reviewer

打开命令输出的 YAML 路径。可以用下面的定义描述代码评审职责，模型与推理参数留空时沿执行工具的默认配置：

~/.runweft/agents/reviewer.yaml
schemaVersion: 1
name: 代码评审
description: 检查变更正确性、回归和验证缺口
instructions: |
  阅读工程约定与相关变更。
  按严重性报告有依据的问题，不直接修改代码。
runtime: null
flavor: null
model: null
reasoningEffort: null

将下面的 <runtime-ID> 替换为刚才复制的实际 ID，再执行：

绑定执行目标
runweft agent validate
runweft agent bind reviewer --runtime <runtime-ID>
runweft agent check reviewer

个人绑定存入 Runweft 数据目录，不改写项目 YAML。需要项目共享定义时，在项目中使用 runweft agent init reviewer --scope project；同名项目定义会整体覆盖全局定义。

04 / DELEGATE

在项目里，发出第一条委派。

进入要工作的项目目录，打开已接入 MCP 的 Codex 或 Claude Code 会话。你可以直接对主 agent 说：

用 Runweft 的 reviewer 检查当前改动，等待它的结果，并总结需要处理的问题。先不要修改代码。

主 agent 会通过 MCP 发现定义、派生任务、等待并读取结果。spawn_agent 返回的是接受状态，实际完成由 wait / read_agent 确认。

也可以先用 CLI 检查完整流程

在实际项目目录运行
runweft workspace bind
runweft agent check reviewer
runweft task spawn reviewer --message "检查当前改动，报告问题，不修改代码"

从输出复制任务 ID，再替换下面的 <任务ID>：

等待并读取结果
runweft task wait <任务ID>
runweft task show <任务ID>
runweft open

等待超时可以再次等待，不需要再派生。看板分别展示执行、代码和附件状态；原生审批和对话沿 HAPI 详情处理。

选择协作方式

共享目录，还是独立 worktree？

模式适合的工作前置条件
本地共享目录在当前现场评审、查询或协作默认模式，可没有 Git
本地独立 worktree隔离代码改动，保留独立现场主目录为 Git 仓库
远端独立 worktree使用另一台机器的 runtime同一 Hub、Git 仓库、显式基线

例如，先创建并绑定一个负责实现的 developer 定义，然后执行：

从已提交的 HEAD 派生独立工作区
runweft task spawn developer --workspace-mode worktree --base HEAD --message "实现任务并运行相关检查"

基线在接受时固定。未提交、未跟踪和 ignored 文件不会自动带入；项目依赖由子 agent 按需安装。远端也使用这条入口，执行位置取决于 Agent 绑定的 runtime。

把成果接回来

继续任务，或审查后合入。

每轮结束关闭子进程，session 和 worktree 默认保留。想在原现场接着做，可以追加下一轮：

复用已有任务
runweft task send <任务ID> --message "继续处理刚才发现的问题"
runweft task wait <任务ID>

本地 worktree 的成果已在同一 Git 仓库；远端成果先从中心取回到原主仓库：

远端代码取回
runweft task result fetch <任务ID>
runweft task result show <任务ID>

确认取回完成后，根据返回的 ref 审查并显式 merge / cherry-pick。取回不修改当前分支，不自动合入或 push。发生交付错误时，先读原因再补交，不通过重跑模型掩盖问题。

文件任务可通过 MCP 的 upload_artifact 提供输入，并在派生时声明输入/输出；完成后使用 download_artifact 保存结果。详细字段、留存与清理规则见完整命令参考。

需要远端时

连接一个共享 Hub。

先让主宿主机器与执行机器连接同一 Runweft 中心。执行机器仍需独立安装原生 runtime 并完成模型登录；发起机的全局 skills、其他 MCP 和凭据不会自动同步过去。

中心：启动公开服务

下面假设已配置反向代理，将你的公开 HTTPS 地址转发到中心 3210 端口。把示例域名替换为自己的地址；中心保留 mode: local。

中心机器 · 前台服务
runweft init
runweft config set server.publicUrl https://runweft.example.com
runweft config set server.runner false
runweft serve --public

在中心另一终端执行 runweft auth token，通过已有安全方式将令牌交给客户端。中心由已有进程管理器运行上述前台命令，重启时保留 --public。

新客户端：连接中心

主宿主机器与执行机器分别执行
runweft init --url https://runweft.example.com
runweft auth login
runweft start
runweft doctor
已经有本地配置，如何切换？

init 不覆盖已有配置。先停止当前连接，再明确设置 Hub 地址和模式：

runweft stop
runweft config set hub.url https://runweft.example.com
runweft config set mode hub
runweft auth login
runweft start

在目标机器登记 machine/runtime，再把 Agent 绑定到该 runtime ID。远端任务只支持独立 worktree，必须指定基线；结果通过同一个中心交付。物理跨机器尚未实测，当前已通过同机独立 Hub / 多 Runner 的真实协作验收。

配置与排错

知道数据在哪，也知道问题在哪。

先查看事实
runweft status
runweft doctor
runweft config path
runweft config check
runweft config show
runweft paths
遇到的情况下一步
找不到 runweft检查 PATH 与解包位置，保留相邻的 Runweft/HAPI。
MCP 已安装，但未连接先检查服务 status/doctor，再检查 mcp check，重新打开原生会话。
机器在线，模型仍报错在执行机器检查原生登录与该账户支持的模型；修改环境后重启 Runner。
等待超时，或响应不明确先用 task list/show 查询原任务，再次等待；不要盲目重复派生。
程序升级，服务仍为旧版根据角色重启服务；doctor 会报告运行版本与安装版本差异。

默认配置是 ~/.runweft/config.yaml。机器/runtime 属于当前中心；全局 Agent 在 agents/，项目 Agent 在项目的 .runweft/agents/。日志、数据库、工作区、附件与 MCP 备份均可通过 paths 定位。

卸载程序不会清理数据。备份前先结束任务并停止对应服务，同时保留 Runweft 数据、原生会话和 worktree 依赖的源仓库。完整配置、附件限额与清理命令见完整命令参考。
