# 账号密码与首次接入技术方案

本方案落实 [需求](requirement.md)，保留身份 UUID、空间、成员及资源授权，将用户认证改为密码登录和独立可撤销凭据。当前以方案审阅为目的；文中“新增”“改为”均为拟实施契约，不是已上线能力。调查事实及外部依据见 [research.md](research.md)，体验变化见 [onboarding-review.md](onboarding-review.md)。

## 架构与职责

| 对象 | 职责与关系 |
| --- | --- |
| Identity | 稳定用户 UUID、显示名称和创建时间，继续作为 owner/user 外键 |
| Account | 单个 Hub 内唯一用户名、密码哈希，1:1 关联 Identity |
| UserCredential | 某次浏览器登录或某台 CLI 的用户凭据，N:1 关联 Identity，可独立撤销 |
| Membership | Identity × Space → owner/admin/member，沿用现有授权 |
| Access JWT | 引用一条 UserCredential 和选定空间，最多有效 15 分钟，使用时重查有效性 |
| Machine / Task credential | 沿用独立执行主体，只访问原来允许的机器、任务或附件 |

HAPI pin 的登录入口只有 accessToken 和 Telegram 数据，用户表是外部身份到 namespace 的映射，不能替代 Runweft 身份/空间。新增逻辑留在现有 Hub 与授权网关；继续使用私有 HAPI 的会话、Runner、文件、终端、SSE 与 Socket。无需修改 HAPI pin、launcher 或原生模型登录。

## 账号、密码和浏览器会话

### 账号注册与密码校验

用户名建议为 3–32 位 ASCII 字母、数字、点、下划线或短横线，首位为字母或数字；前后空格去除，大小写统一后按唯一索引判断。用户名首版固定，显示名称可修改。注册仅收用户名和密码，显示名称默认取用户名。

密码建议 15–128 个 Unicode 码点，允许空格、粘贴和密码管理器，不截断、不 trim、不强制大小写数字符号组合，不定期强制更换。使用 Bun 1.4.2 的异步 `Bun.password.hash/verify`，Argon2id 参数显式固定为至少 19 MiB、2 次迭代、并行度 1；PHC 字符串包含盐和参数。性能在目标平台实测后决定是否提高成本，不能以未经测量的性能目标作为验收事实。

登录统一返回“账号或密码不正确”；不存在的用户名执行固定假哈希验证以减少明显计时差。注册的用户名冲突以可操作的错误提示处理。注册与登录都在哈希前限流，并限制昂贵哈希的并发；基础方案按来源 IP 和规范化用户名双维度限制，首次不引入验证码或外部风控服务。公开入口只允许 HTTPS，真正的 loopback 开发入口允许 HTTP；不盲信请求提供的转发 IP。

异步哈希在数据库事务外运行，提交时重查当前账户及凭据。创建账号、Identity、初始空间和浏览器凭据在一个短事务提交。重复用户名或丢响应后不会再创建另一个身份；客户端只在原用户名下尝试恢复登录，不静默修改输入。

### 浏览器凭据取舍

首版沿用当前 Hub 的标签页隔离方式：登录返回短生命周期的随机浏览器会话凭据，应用自行写入该标签的 `sessionStorage`，只通过 Authorization 头访问账户接口；页面不展示、不提供下载或复制。建议绝对期限 12 小时、闲置期限 2 小时，服务端维护期限和撤销状态，UI 活动不无限延长绝对期限。刷新保留登录；关标签后账号密码重新登录。

这不是把浏览器会话当作长期身份：身份与权限独立，凭据有明确失效时间、单独撤销和会话列表。服务端仅保存 32 字节随机秘密的摘要；浏览器会话和 CLI 凭据使用不同前缀并校验种类。

**选择理由与限制**：当前 Hub 与受限 HAPI 页同源，原生页通过清除继承的会话存储、断开 opener、只注入短 JWT 来限制访问。直接换成同源自动携带的 Cookie，原生页也能带 Cookie 调用账户／换票接口；HttpOnly、Path 或 SameSite 不能提供标签级隔离。首版保持当前拓扑与原生页权限边界，不为了登录增加第二个公网 origin 或改造 HAPI 页面协议。

Web Storage 对同源脚本可读，无法抵御该页面的 XSS；OWASP 因此优先推荐 HttpOnly Cookie。此处是基于现有隔离架构的明确取舍，不宣称比 Cookie 更安全。沿用严格 CSP、无第三方脚本、`textContent` 渲染、无 URL 凭据和不持久化密码，并回归原生新标签清理。未来若要求“关闭浏览器后长期记住登录”，须先设计账户与原生页的 origin 隔离，再采用 Cookie；本 Change 不增加跨浏览器重启登录承诺。

### 账户接口边界

下表为拟定接口，统一在 `/api/runweft/hub` 下；登录/注册/重置不允许跨域，JSON 大小限制沿用当前边界。

| 接口 | 行为 |
| --- | --- |
| `POST /accounts` | 用户名+密码注册，返回公开 identity/space 与仅浏览器消费的会话凭据 |
| `POST /sessions` | 密码登录，创建独立 browser 凭据；不复制旧会话 |
| `GET /identity`、`PATCH /identity` | 保留身份查询与显示名修改，改用当前用户凭据认证 |
| `POST /sessions/logout` | 撤销当前 browser 会话，成功或已撤销后清理本地记录 |
| `GET /credentials`、`DELETE /credentials/:id` | 本人登录环境的名称、类型、创建/最近使用/到期时间，单项撤销；不返回秘密/摘要 |
| `POST /credentials/revoke-all` | 浏览器重新验证当前密码后撤销全部用户凭据，包含已确认但本地尚未保存的 CLI 凭据 |
| `POST /account/password` | 当前密码+新密码，事务更新后撤销全部用户凭据；返回登录页 |
| `POST /account/password-reset` | 用户名+有效一次性重置码+新密码，消费后返回登录页 |

账户管理、凭据列表/撤销和新的 CLI 授权确认要求直接提交有效的原始 browser 会话秘密；派生的短 JWT 即使 ref 指向 browser 凭据，也不能调用这些入口。CLI 凭据不可调用这些安全敏感操作，单个 CLI 仅可通过专用 logout 撤销自身，或取消自己的待连接请求并撤销该请求对应的凭据，不能据此重置账号或创建另一台 CLI 的授权。身份/空间等已有业务接口继续允许合法用户凭据。账号设置把“退出浏览器”和“断开命令行环境”明确显示，避免与 Runner 停机混淆。

## CLI 连接协议

保留 `hub connect begin` → 浏览器明确确认 → `hub connect complete` 的现有入口及核对码。改变交付物：CLI 获得自己独立的凭据，浏览器不会把自己的会话复制过去。

采用用户已采纳的“确认即激活”方案，以客户端生成的随机秘密替代旧 RSA 交接：

1. `begin` 先在权限为 0600 的本地 `connect.json` 待连接记录中保存新 CLI 秘密、原 requestId、Hub 和旧连接指纹，再向 Hub 登记其摘要、设备名和期限。该秘密同时用于查询或取消本次请求；未确认时不能访问用户 API。
2. Hub 返回无秘密的 `/hub#connect=<requestId>`、设备名、核对码和 10 分钟确认期限。公开查询仅显示确认所需的非秘密字段。
3. 用户在浏览器注册／登录并确认。服务端首次确认时验证原始 browser 会话、request origin、请求尚未取消或过期，以及当前身份和目标空间成员资格；在同一事务内用登记的摘要创建并激活唯一 CLI 凭据，记录 owner、默认 space 和实际 credentialId，将请求置为 confirmed。此时 CLI 已持有的秘密即可访问获授权的用户 API。相同身份和空间的重复确认仍校验当前 browser 会话与成员资格，按原凭据当前状态返回，不重复创建、不改绑身份或空间；已取消、已撤销或凭据到期的请求不重新激活。
4. `complete` 用原秘密查询请求状态，pending 时有界等待，confirmed 后核对原请求和授权上下文，再用该凭据验证远端身份、当前成员资格及本机机器归属。通过后原子保存连接文件、保存 Hub 配置，完成后清理待连接记录并报告 connected。重试只验证并保存已有授权，不增加激活请求。

客户端已经持有最终随机秘密，Hub 只需保存摘要，无需交接密文或等待领取确认，因此移除 ACK 接口和 consumed 状态。`confirmed` 表示浏览器已完成授权并激活凭据；`connected` 仍是 CLI 验证与本地保存完成后的结果。必要的 `connect.json` 继续承载原秘密与请求上下文，不另建待 ACK 回执文件；它在网络中断、进程退出或保存失败后支持原请求续接。公开 requestId 仅用于查询公开摘要，受保护的状态查询、取消或用户访问仍需本机秘密。

确认响应丢失或本地保存失败时保留待连接记录，使用同一秘密和 requestId 查询、验证及续存；不创建第二条凭据，不覆盖后来改变的连接。若明确发现本机机器归属冲突，则保留原连接并取消这次授权；网络结果未知时保留待连接记录核实，不把失败当成已取消。CLI 未回来完成保存时，已确认凭据仍出现在登录环境列表中，可被撤销或按自身期限到期。

连接确认展示授权效果：该命令行环境能以当前账号使用其有权访问的资源；选定空间是默认工作空间，不伪称凭据只授权这一个空间。后续显式 `--space` 仍须符合当前成员资格，每次短 JWT 固定实际空间。CLI 凭据建议最长 90 天，到期明确要求重新浏览器授权，不新增后台刷新 token 系统。

确认期限只约束 pending 请求能否获得授权。确认后按 CLI 凭据自身期限、撤销状态和当前空间成员资格检查；即使原十分钟期限已过，只要这些条件仍满足，`complete` 仍可完成保存。密码修改、重置或全端退出会撤销已激活凭据，旧浏览器会话不能再确认请求；恢复或重复确认均不能重新激活已失效凭据。未确认请求尚未绑定用户，仍按自身期限等待重新登录后的明确授权。浏览器普通退出不撤回已经明确授予的 CLI 授权。

`hub connect cancel` 针对本地待连接记录中的原请求：确认前将请求取消且不创建凭据；确认后在同一事务内撤销该请求关联的凭据并取消请求。确认与取消并发时以事务结果为准，取消成功后不会留下有效的新凭据；重复取消返回同一结果。取消结果确认后才清理本地待连接记录，结果未知时保留以供重试，原有其他有效连接保持不变。已完成保存并清理待连接记录的 CLI 使用 logout 注销自身。

移除 `rw_id_` 用户认证、`--identity-file`、`RUNWEFT_IDENTITY_TOKEN` 及身份备份导入。新 CLI/MCP 只从当前 Hub 的受限连接记录获取用户凭据，不提供命令行密码参数，也不让模型读取用户密码。

## 网关与撤权语义

用户 JWT 的 `sub` 仍为 Identity UUID，`ref` 改为具体用户凭据引用，不再直接绑定 `hub_users.tokenDigest`。验证签名和期限后，重新读取凭据的所属身份、种类、到期/撤销状态及空间成员资格；不能只验证 JWT 签名。browser 凭据派生的 JWT 不允许超出其剩余期限。

| 事件 | 用户访问 | 已接受任务 / Runner |
| --- | --- | --- |
| 退出当前浏览器 | 仅该会话和派生 JWT 失效 | 已接受任务继续，其他登录及 Runner 保留 |
| 撤销某 CLI | 该 CLI 和派生 JWT 失效 | 已接受任务继续，独立 Runner 凭据保留 |
| 修改/重置密码、退出全部 | 所有 browser/CLI及派生 JWT 失效，包含已确认但本地未保存的 CLI 凭据；旧会话不能再确认请求 | 不自动重放或停止任务；机器凭据保持独立 |
| 移除空间成员、撤回资源许可 | 当前空间许可按现有规则撤销 | 继续使用现有任务停止、附件/派生许可撤销机制 |
| 撤销机器凭据 | 机器执行通道失效 | 沿用机器撤权处理，不等于用户账号退出 |

后台协调器已接受的任务按固定 owner/space 继续授权，不依赖发起浏览器或 CLI 凭据是否存活。替换目前 `serviceUser` 读取长期身份摘要的实现，以可信内部入口构造服务主体；该入口只接受服务端已持久化的 owner/space，不允许 HTTP/JWT 声明自己是内部主体。成员/资源撤权仍需检查，不能用内部入口绕过。

HTTP lease、Socket、SSE 和文件流继续复用现有动态检查，空闲长连接按现有最长 1 秒检查退出。撤销登录仅终止访问通道，不重新派生任务。恢复登录后可通过本人任务目录找回历史。

## 部署者协助重置

新增本机管理命令，例如 `runweft --home <Hub目录> account reset-password <username> --output <受限文件>`；命令名称在实现前固定。它只操作已有本机 Hub 数据库，不使用远端用户 API，不因为空间 owner/admin 角色而可调用，不初始化缺失数据库。

部署者须具备该数据目录的 OS 访问权。命令生成 15 分钟一次性重置码，服务端只保存摘要，完整码写入显式指定的 0600 新文件，不进入 stdout、日志、命令参数、URL 或 Agent 对话。普通输出只报告账号、期限和文件位置。部署者通过自己的可信渠道交给该用户，用户在浏览器的“重置密码”表单使用。

同一用户最多一个有效重置码，新签发替换旧码。签发本身不注销用户，成功消费和密码更换在一个事务中完成，并撤销原有用户凭据，包含已确认但本地尚未保存的 CLI 凭据；旧浏览器会话不能再确认请求。重复消费失败。密码哈希在事务外计算，提交时重查码期限和有效性，避免并发重复消费。重置后回登录页，用户名可预填，密码不持久化。此恢复流程不需要邮件基础设施，也不保存用户长期恢复秘密。

## 首次体验的 CLI 工作流

编排继续由主 Agent / Runweft Kit 承担。复用现有小命令，不新增通用 setup 工作流引擎或服务器后台自动业务编排。

| 阶段 | Agent/CLI 动作 | 用户动作 |
| --- | --- | --- |
| 检查与安装 | 检查版本、现有连接、宿主及工具；按授权安装程序、Skill、MCP；仅管理自己的配置 | 一次接入指令已给出授权；冲突时才补充决定 |
| 确定 Hub | 指定地址→既有连接→首次默认本机；检查健康与能力后使用 | 常规首次无需额外选择 |
| 获取账号授权 | begin 保存待连接记录；展示链接；complete 有界等待授权、校验并保存 | 一张表单注册/登录并确认，确认即激活该 CLI 凭据 |
| 准备执行 | enroll→associate→runner start→discover→runtime register/check；复用有效 ID | 已登录工具正常时无需操作 |
| 关联当前项目 | repository inspect/match；依据明确当前cwd/远端创建或选择已有仓库并绑定本人checkout | 歧义或基线不可用时才补充决定 |
| 准备首个 Agent | 查个人默认或明确已有定义；没有时创建私有只读评审 Agent 并保存返回 UUID | 无需填写模型、UUID、提示词或共享选项 |
| 第一份结果 | task spawn→wait→show，保留 requestId，读完整报告 | 已授权只读任务正常时无需追加提示 |
| MCP 状态 | 安装和 check；当前宿主可调用时实际调用；需要重载时说明一次 | 必须时重载宿主，之后验证 MCP |

用户无需手工配置 Repository，但 Git 目录的 shared 模式仍经过现有仓库匹配。Agent 先 inspect/match：matched 复用；未匹配且当前仓库和远端明确时以固定 requestId create 后 bind；唯一候选未绑定时绑定本人 checkout；多个候选或远端歧义再询问。无远端可创建不带 alias 的仓库并绑定；真实 non_git 目录沿用原路径，Git 读取失败不能伪装 non_git。HEAD/基线不可用时给出具体条件，不擅自提交用户代码。worktree、远端执行和资源分享按需配置。

已有 Agent 名称不能作为唯一键，不按同名猜测绑定；用已有个人选择、连接记录和明确返回 UUID 复用资源。

可新增的小能力限于：`connect complete --wait <秒>` 的有界等待、账户/CLI 凭据的登录与注销管理，以及清楚的连接结果：pending 表示等待确认，confirmed 表示已授权激活，connected 表示 CLI 校验与保存完成；请求过期、取消或凭据失效给出对应原因。普通 stdout/JSON 只输出非秘密状态，等待应响应取消并让 Agent 定期反馈。Agent 依据各领域事实恢复，不增加重复的全流程数据库状态机。

第一次真实模型任务须包含在用户接入请求的授权中；若用户只要求安装，不自动调用模型。用户的原生登录和权限审批仍按客户端机制进行，Agent 不代填密码、修改模型凭据或放宽原生执行权限。

## 连接页与成功态

新用户页只展示用户名、密码、Hub/设备核对信息和“注册并连接”。注册与授权的 UI 意图可一次提交，后台仍明确区分账号创建成功和 CLI 确认成功；连接已过期时保留新账号，提示 Agent 为同一账号重新发起连接，不重复注册。

已存在的账号使用“登录并连接”；多个空间时在同页显示选择器，单一空间用已选摘要。Agent 链接通常打开新标签，不能继承另一个标签的 Hub 登录状态，默认仍需登录，可用密码管理器自动填充。只有承载连接页的标签已保存有效会话且身份正确时，才跳过密码输入、仅显示授权确认；若该标签的身份不符合预期，提供切换登录入口。

确认后页面显示“已授权，可以返回对话；Agent 会继续完成接入”。此时该 CLI 凭据已经激活，本机 connected 仍须由 CLI 完成远端校验及本地保存后报告；不增加一套网页端全流程就绪追踪。机器和模型任务完成也由 CLI 结果报告，不把网页确认作为执行就绪。直接访问 Web 的用户注册/登录后进入普通工作台，不强制安装 Runner。

实施前在项目原型包覆盖注册并连接、已有账号登录、过期请求、恢复密码、撤销环境和首次空态。保持页面标签、原生表单自动填充、键盘焦点、错误关联和 `aria-live` 状态；不把长 UUID、协议和技术状态作为默认用户任务。

## 数据格式与发布处理

Q1 已明确无部署和无兼容需求。基于当前中心 schema 19，集中定义下一唯一格式（无并发格式变更时为 20），重建 `hub_users` 的凭据结构，新增账号、用户凭据、密码重置记录并改造连接请求结构；不读取旧 schema 19。新的 `identity.json`/`connect.json` 有独立当前 schema，旧记录拒绝且保留，不自动删除重新登录。

建议将登录名称与密码记录放 `hub_accounts(userId, username, passwordHash, passwordChangedAt)`；`hub_users` 保留 `id/name/createdAt`。`hub_user_credentials` 保存 `id/userId/kind/tokenDigest/label/createdAt/lastUsedAt/expiresAt/revokedAt`，浏览器闲置判断使用 lastUsedAt，更新可有界合并以免每次只读请求写库。重置码表保存用户、摘要、到期、消费信息；连接请求引用拟授权摘要和实际 credentialId。唯一性和外键由数据库约束。

client.sqlite 的现有 schema 若无需新增字段则保持 1，config.yaml 保持现有部署语义；机器记录和 HAPI 数据格式不为此次用户登录变化自动升级。最终列清所有变化的格式标识，与 [首次部署基线](../../specs/deployment/spec.md#当前数据格式) 一起在实现验收后更新。

服务与客户端通过新能力标识核对账号/连接协议后再发送凭据，版本不匹配明确失败。旧格式预检继续在产生服务副作用前执行；拒绝时保留数据库、WAL/SHM和连接文件。测试需要新目录，由验收自行创建隔离环境；产品不增加数据 reset 或清理入口。回退仅在保留原程序与原目录的情况下操作，不让旧程序读取新格式。

## 实施顺序与验证路径

先固定并评审需求/方案，完成相关交互原型后再制定 large Change 的任务计划。推荐按用户场景组织实现：账号注册登录及退出；单环境授权和撤销；密码修改/恢复；CLI 首次体验与文案；跨通道与任务回归。每个场景的实现、测试和文档一起交付，不按“先所有表、再所有 API、最后补测试”割裂。

首个场景须同时交付账号/凭据结构拆分与 `serviceUser` 按稳定 owner/space 构造内部主体的改造，避免删除 `hub_users.tokenDigest` 后后台任务授权失效；后续 Plan 将这两项放在同一交付任务内。

实现使用独立分支/worktree。当前蓝色后台原型是另一个 Change，实施前核对其实际归属，协调同一原型包及 Hub 壳的改动；没有已确认的功能依赖，不登记虚假 dependsOn。

| 验证 | 复用入口与主要断言 |
| --- | --- |
| 账户/空间 | hub.test、web-identity：唯一用户名、密码校验、UUID稳定、初始空间、退出重登、角色不扩权 |
| CLI 连接 | cli-connect、web-connect：一页确认即激活、重复确认不重建凭据；本地待连接记录支持丢响应/保存失败续接；确认前过期拒绝、确认后按凭据期限恢复；确认前取消请求、确认后取消撤销凭据；0600与秘密扫描 |
| 当前仓库 | hub-repositories、hub-delegation：首次Git目录的create/bind、唯一匹配复用、歧义不猜测、真实non_git与读取失败区分 |
| 会话与授权 | hub-access、hub-realtime-live、files-access：单会话及全端撤销、JWT到期、Socket/SSE/流中撤权 |
| 原生 UI | hub-console、console-tasks：短 JWT不续期/不改空间、无浏览器凭据继承、不能进行账号操作 |
| 后台任务 | hub-delegation：退出/改密码使用户 wait 失效但已接受任务继续，成员撤权仍停止 |
| 数据 | core 格式拒绝与并发建库：新格式约束、旧格式原字节/WAL/SHM保全 |
| 首次体验 | Playwright 记录常规路径表单和确认次数；独立 Agent 场景验收 Kit；在已授权专用环境真实 CLI 模型任务读回报告 |
| MCP | 独立核对安装/握手/实际原生调用，不以 CLI 模型任务替代 |

执行前由 `ci-scope` 选择检查，按 [测试手册](../../../testing.md) 定向执行；失败先诊断续验。本轮只有代码/文档调查、合成密码 API 可用性检查及现状截图，未证明新账户方案可运行。

## 必要机制与范围控制

| 处理 | 机制及具体原因 |
| --- | --- |
| 保留 | 密码哈希、有限会话、限流、单次重置码：保护公开登录入口与账号接管恢复 |
| 保留 | 连接核对、显式确认、固定请求 ID：避免授权错误设备和未知结果重复创建 |
| 保留 | 动态撤权、后台任务稳定归属、HAPI短凭据：满足已有权限与恢复契约 |
| 合并 | 注册/登录与连接确认呈现为一张表单；显示名/初始空间使用默认值 |
| 合并 | 浏览器确认与 CLI 凭据激活在一个事务完成；保留本地待连接记录供 CLI 校验、保存和失败续接 |
| 合并 | 由 Agent 串接现有 CLI 完成安装、资源准备和首份报告；MCP重载移出首份结果前置 |
| 删除 | 用户身份 token 备份/导入/轮换、浏览器向CLI复制同一秘密、ACK激活与consumed状态、旧格式兼容与迁移设计 |
| 延后 | 邮箱/短信/SSO/MFA、长久记住登录、跨origin部署、通用工作流引擎；没有本次用户需求或必要事实支撑 |

浏览器凭据存储及同源原生页边界是需要在方案评审中显式接受的取舍；不以“简化体验”掩盖 Web Storage 的 XSS 风险，也不为了账号登录扩大空间管理员的内容权限。
