# 端口转发下的账号连接授权

延续已归档的 account-password-onboarding，修复 CLI 在开发机通过 `127.0.0.1:3210` 发起连接、用户通过另一主机名或端口打开同一 Hub 时被拒绝的问题。用户已确认按前次调查方案实施，补齐转发测试和 Skill，并将本地构建与 Skill 安装到当前机器全局试用；正式发布等待用户确认。

## 行为与方案

- CLI 的 Hub 地址继续用于通信、待连接记录及凭据分区；浏览器通过已建立的转发入口访问同一请求，页面 API 保持当前页面同源。浏览器地址不再与 CLI 登记地址作字符串相等判断。
- 浏览器来源在 HTTP 入口与实际 Host 校验；确认仍要求当前 Hub 的有效请求、有效 browser 凭据、明确用户确认和空间权限。CLI 持原请求秘密完成连接，保留确认即激活、重试和取消语义，不增加新握手或数据格式。
- Skill 指导 Agent 使用转发工具返回的入口转换给用户的确认、后台及任务链接，保留路径、查询参数和 fragment；CLI 仍使用其自身可达的 Hub 地址。Skill 不固定 beta 版本、不代收密码，不自动创建公网导出。
- 使用正常 npm 打包布局安装当前平台的本地构建及配套 HAPI；只更新 Runweft 的全局包和已有产品 Skill，保留其他工具、模型凭据和原生配置。现有 1.1.8 数据保留，试用采用独立当前格式数据目录。

## 验收

1. Playwright 通过保留 Host 的真实端口转发，在不同主机名和端口下完成注册并连接、另一环境登录并连接、已登录标签确认；CLI complete 成功保存原 Hub 地址，原请求重试不重复发凭据。
2. 通过转发打开 CLI 生成的任务链接，登录后显示原任务报告；直连仍通过，其他站点的 Origin、无效请求及无权身份继续拒绝。
3. Skill 结构检查和独立 Agent 场景验收通过，Agent 能区分两种地址并映射完整链接，不要求用户改成相同端口或交出密码。
4. 全局程序能报告本地构建版本，实际执行文件与本地构建一致，包内及全局 Skill 与源码一致。完成本机隔离转发回归后交用户体验。

用户要求本机人工确认后再正式发布；本 Change 完成实现和自动验证后等待用户验收，不提前发布 npm、同步公开 Skill、合入 main 或归档。
