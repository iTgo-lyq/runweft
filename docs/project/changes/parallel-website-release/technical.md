# 技术方案

见 [需求](requirement.md)。用户已接受两端短暂不一致；采用两个并行工作流分支，不引入预览晋级或站点动态版本指针。

## 方案

npm 工作流的 website job 取消 beta/promote 依赖，通过不可变 tag 的规范版本和 package.json 选择稳定发行；空预检、Beta 和 verify-run-id 不调度官网。网站仍 dispatch main，携带精确版本、父 run/attempt 和显式 parallel 标识；官网核对 main 版本与当前提交，并仅对该显式模式跳过 npm 上线前检查。父流程等待返回的真实子 run，summary 汇合 npm 和官网的必需结果。官网先成功不改变 npm 验收/晋级顺序，官网失败不阻止另一分支完成，但整体失败如实保留。

站点十文件校验复用三分钟共享预算，单请求至多剩余预算与三十秒的较小值。200 且 MIME 正确但摘要不符时重读，记录有限的状态/摘要/目标主机证据，不记录响应正文。正确字节才接纳；错误 MIME、鉴权和项目外跳转不放宽。

website-pages 显式 verify-run-id 从同仓库网站 workflow 的原 job 日志提取静态检查与上传回执，绑定原 head、分支和环境，核对当前构建十文件与原记录完全相同。复用原 URL 进入在线验证和浏览器步骤；准备项目和上传 action 均跳过，保留来源 run 证据。原源码提交可不同，但当前静态产物必须完全一致，生产仍核对 main 当前提交。

## 影响与失败处理

官网可能在 npm 尚不可安装或后续验收失败时显示目标版本，这是用户明确选择的发布取舍。失败不自动回滚已上传网站、不覆盖 npm 版本；状态未知先查已有回执。原存档只读，新验证写本 Change。普通官网变更和 Beta 行为保留，不扩展模型验收或修改用户配置。

## 验证

用工作流断言、HTTP/日志夹具覆盖并行模式、总结果、超时和来源拒绝；以 1.1.6 已部署站点做只读十文件及浏览器复验；分支 CI 和实际 iclaude 独立复核覆盖最终差异。新不可变版本的真实 npm 并行墙钟另需正式发布，不把旧版本复验写成新发行性能证据。
