# Change 边界与分阶段交付

> 更新：2026-09-29
> 性质：本轮拆分审查与调整方案，不代替各 Change 的 Technical/Plan，不表示功能已实现。
> 目标：保留完整版本范围，使每个 Change 消费已明确的上游契约，并能在后续模块缺席时验证自身结果。

## 拆分审查结论

原十个 Change 的主题大体合理，但存在文档依赖图没有表达的耦合：

| 原边界 | 问题 | 调整 |
| --- | --- | --- |
| 本地独立模式依赖远端准备 | 本地 Git 能力被附件、跨机传输和远端启动拖住 | 本地工作区 Change 先交付独立 worktree 与公共 Git 生命周期，远端准备消费它 |
| 宿主 MCP 整体依赖委派 | 调度又需要宿主身份与禁止递归，形成隐含反向依赖 | 宿主适配前置，只负责身份、角色、工具暴露与结果传递机制；委派 Change 拥有实际协作工具和本地共享流程 |
| 委派、MCP、本地共享分别验收 | 派生到结果返回没有一个完整负责方 | 委派 Change 负责 CLI/MCP 本地共享目录的完整协作验收 |
| CLI 同时负责基础运行和完整发行 | 基础入口无法早验收，所有模块都可能回流修改“统一 CLI” | CLI 负责安装基础、服务配置和命令承载；各领域自带命令，新增完整版本集成与发布 Change |
| Git 收尾仅放在远端结果中 | 本地与远端会重复定义保留、提交失败和成果引用 | 本地工作区 Change 拥有公共 Git 准备与封存；远端结果只增加跨机交付、验证与取回 |

保留现有十个目录并重定边界，新增全局机器/runtime 注册和完整版本集成与发布两个 Change，共十二个。资源注册独立于 agent 配置，但机器与 runtime 仍是两类身份，不能合并成同一条注册记录。已确认行为继续有效；2026-09-29 用户进一步确认独立 worktree 自动 checkpoint 与默认 bundle 传输，具体清理期限与配额在正式方案中落实。

## 阶段与可验收结果

阶段是推进顺序，不是另一套任务状态。允许先调研后续模块；实现按前置能力及契约就绪情况推进。每个阶段完成只代表其范围通过验收，最终交付必须覆盖全部阶段。

| 阶段 | Change | 该阶段可独立证明的结果 | 不需要等待 |
| --- | --- | --- | --- |
| 1. 运行与接入基础 | [统一 CLI](changes/unified-cli-and-deployment/requirement.md) → [HAPI 执行契约](changes/hapi-subagent-foundation/requirement.md) → [宿主适配](changes/host-mcp-adapter/requirement.md)；[资源注册](changes/execution-resource-registry/requirement.md)依赖 CLI，[Agent 定义](changes/agent-definition/requirement.md)依赖 CLI 与资源注册 | 本地/Hub 模式、统一数据布局与基础安装可用；机器/runtime 分别全局注册；MCP 可一键辅助全局安装；两种 runtime 在已准备目录可靠执行/停止/续接；两种宿主身份与角色分流有真实证据；agent 定义可解析 | 委派数据库、Git 工作区、附件、远端业务链路、看板 |
| 2. 本地共享协作 | [委派生命周期](changes/delegation-lifecycle/requirement.md) | 从原生宿主通过 MCP 派生本地任务，等待、收回报告、中断和追加；每轮结束关闭执行，保留 cwd/session；CLI 调用同一能力 | 独立 worktree、中心附件和远端环境 |
| 3. 工作区与文件交付 | [本地独立工作区](changes/local-workspace-execution/requirement.md)、[任务附件](changes/task-artifact-delivery/requirement.md) | 前者在本机独立 worktree 完成协作、封存与续接；后者在无 agent 会话时完成文件上传、下载与保留；阶段组合验收启动前输入和任务输出附件 | 远端 Runner 上的仓库传输、远端成果回收、看板 |
| 4. 远端完整协作 | [远端准备](changes/remote-workspace-preparation/requirement.md) → [远端结果](changes/remote-result-delivery/requirement.md) | 精确基线与附件先到达，远端执行后主仓库取得可合入成果；失败重试与续接可验证 | 看板和最终发行整合 |
| 5. 全局可见性 | [Subagent 看板](changes/subagent-dashboard/requirement.md) | 使用已有查询事实展示跨工作区、机器与父任务状态，链接 HAPI 详情 | 看板基础验收只需阶段 2；完整交付状态组合在阶段 4 后验证 |
| 6. 完整版本交付 | [集成与发布](changes/integrated-release/requirement.md) | 同一候选发行版本安装、配置、完整协作和诊断可运行；两宿主、两 runtime、本地/远端及 macOS 证据齐全 | 不以任何后续功能补齐本次承诺 |

阶段 1 在 CLI 基础安装可用后可分别推进执行与资源注册的证据核对；宿主消费执行契约，agent 定义消费资源注册；图中依赖仍约束对应实现。宿主无法可靠识别子角色或隔离工具列表时，先解决该缺口，不带着假设进入阶段 2。

阶段 3 两个 Change 不相互依赖。附件 Change 负责将文件能力接入既有任务输入/输出；公共 Git 准备只接受已解析的本地输入路径，不直接调用附件中心。其对象服务可单独验收，任务组合使用阶段 2 已有委派，不依赖本地独立模式完成。阶段 3 结束时再验证两者组合，不修改各自语义。

阶段 4 的准备 Change 可用专用准备请求和原生启动验证独立验收，不要求先有结果服务。完整远端代码委派必须同时具备准备与回收能力才开放；不能把“远端能启动，但成果只能留在远端”当成已交付功能。

## 唯一职责与契约提供方

| 能力 / 数据 | 提供方 | 消费边界 |
| --- | --- | --- |
| 安装布局、HAPI 连接与认证、服务运行位置、工作区绑定、公共数据位置及命令承载 | 统一 CLI | 不保存业务轮次或重复 HAPI 会话；各 Change 拥有自身命令、配置和数据迁移 |
| 原生执行身份、接受/终态证据、停止与恢复 | HAPI 内置能力验证与调用封装 | 沿已有 Codex/Claude Code 适配验证和调用，不主动改造 runtime；不要求知道 delegation、附件或成果结构 |
| 宿主可信身份、主/子角色、工具暴露与结果传递机制 | 宿主适配 | 同时拥有全局 MCP 安装；不调用委派来判断角色；受控子身份在启动前绑定，原生子身份按宿主证据识别 |
| 全局 machine/runtime 注册与执行目标解析 | 资源注册 | 机器是执行主机，runtime 引用机器并表示工具环境；不保存业务职责，不进入项目作用域 |
| 全局/项目 Agent 描述与解析后的执行参数 | Agent 定义 | 不自行调度；运行时默认配置继承由 HAPI 保证，模式组合由消费者验收 |
| delegation/round/result 关联、协作工具、串行轮次和状态查询 | 委派生命周期 | CLI/MCP 共用；禁止递归在入口执行；不复制原生历史库 |
| 仓库/环境/准备身份、Git 基线、worktree 生命周期及固定成果引用 | 本地工作区执行 | 本地与远端共用，在 HAPI 内落实执行侧动作；不包含网络传输、中心存储或另一套执行器 |
| 不可变文件、上传发布、保留引用与配额 | 任务附件 | 不解析 Git 或维护任务状态；任务引用由委派/成果提供方核实后登记 |
| 跨机 Git 来源传输、输入落地及远端准备编排 | 远端准备 | 消费公共工作区能力和附件，不重复实现 worktree 与本地 Git 收尾 |
| 远端代码对象交付、依赖保留、主仓库取回与交付状态 | 远端结果 | 消费固定 Git 成果；不重新判定原生终态或另建自动提交实现 |
| 用户可见全局概览 | 看板 | 只消费委派查询与 HAPI 详情；不直接写任务表或发明另一套状态 |
| 候选版本组合、正式安装与端到端验收 | 集成与发布 | 不接收未实现领域功能；缺陷回到原 Change 修复 |

委派在阶段 2 就定义“启动前准备已完成”和“停止写入后本轮收尾已固定”两个条件，以及报告、执行状态与交付状态的查询表达。共享目录按其实际模式满足条件，不假造 Git 成果。后续工作区和远端 Change 提供这些条件的具体证据，不修改原生执行状态定义，也不引入可插拔 workflow 引擎。

各契约正式进入 Technical 时，必须写明调用方、提供方、必要输入/输出、错误、请求关联、兼容范围和验证方式。具体进程/存储位置须由阶段 1 落实；本表不是让各模块自行选择一套服务框架。

公共 Git 工作区若确需补齐 HAPI 管理入口，归工作区 Change；这不构成修改 Codex/Claude Code 原生适配的理由。私有 runtime 接入在独立项目后续推进，不阻塞本轮完整版本。

## 验收责任

用户已明确本地验收由 agent 自动完成，包括安装、MCP 全局配置、双运行模式、数据持久性、协作及看板，不要求用户逐项操作或批准验收。本机服务可用于 Hub 协议自动测试，真实跨机路径仍单独取证；需要远端机器或访问条件时才安排用户参与。

该指令覆盖项目工作流默认的本地人工验收惯例；不等于可以伪造缺少的 macOS/原生运行证据，也不等于开发中可直接改写用户现有凭据或客户端配置。自动化先使用专用环境，环境不足如实记录并主动解决。

## 推进约束

- 同一工作区一次实现一个中型或大型 Change。明确无共享写入且契约稳定后，才可在独立工作区并行；阶段表不自动授权并行改公共代码。
- 进入下一 Change 前，其直接前置能力已实现并验收；测试替身可验证错误分支，不能替代真实 runtime、宿主和远端链路验收。
- 各 Change 的 Technical 明确主要改动范围；CLI 注册、类型导出等组合改动由当前领域负责，跨领域语义修改回到契约提供方记录影响。
- 各 Change 完成时必须能通过自身验收，不能以“待全量联调”代替完成；最终发布另验证组合与正式安装。
- 阶段中间版本不能宣传尚未具备的模式。相关能力未就绪时明确不可用，不静默切成共享目录、文本报告或模拟执行。
- 集成 Change 只整合已验收能力和补齐发行证据；发现领域缺口返回对应 Change，不在最后一阶段集中实现剩余功能。
- 拆分只改变实现归属与顺序，不削减完整版本范围，不重问已确认的产品选择。
