# 本地共享委派技术方案

> 来源：[Requirement](requirement.md)、[Research](research.md)
> 更新：2026-09-29
> 确认方式：用户已授权自主细化并按顺序交付；Plan 在当前工作区经一次 iclaude 评审，主 agent 独立采纳后实施。

## 架构与边界

复用固定 HAPI 的进程、消息、原生观察、默认权限与 archive/resume；Runweft 中心只新增业务父子/轮次关联、接受去重、准备/收尾协调和结果视图。协调器运行在已有 serve 进程，MCP 与 CLI 只是客户端，父连接关闭不会留住子进程或取消已经接受的任务。

用户流程与工具参数见[协作契约](contract.md)；持久数据、推进次序和未知结果见[中心协调](coordinator.md)。前期 [Design](design.md) 中的环境/Git/远端原则继续适用，具体未实现模式当前明确拒绝。本文及两个契约文件是本 Change 的正式实现依据。

当前仅交付发起机共享 cwd，支持非 Git。AgentClient 的配置发现与目标快照已验收；业务接口不新增 agent 控制台或自动选择器。Hub 可部署在另一位置，但执行机器必须是发起机；后续远端能力就绪后才开放其他机器目标。

## 身份、认证与权限

MCP 使用已验证的逐调用原生身份，中心按父会话限制操作范围。CLI 是显式操作者入口，按当前 namespace 操作任务，不接受伪造原生 session 参数。两者共用服务接口、HAPI 认证与受控子检测，子 shell 的 HAPI_SESSION_ID 从既有 launcher 继承；原生内置 subagent 的递归不受 Runweft 管理。

权限沿 runtime 默认，角色以本中心实际创建的 child 关联为准，不查询外部 Hub metadata 推断角色。查询暴露原生 pending request 与 HAPI 详情入口，显式响应绑定当前 round/request，不增加 yolo、会话级自动批准或额外沙箱。配置与模型凭据继续属于原生工具；日志不保存完整 prompt/源码/秘密。

## 就绪性与限制

已有入口足以构造方案，不预设 HAPI 适配改造。Codex 活跃追加须使用已存在的 queued-message steer 路由，不能把 deliveryMode=steer 当作已接通；Claude 活跃追加明确不支持，下一轮排队与中断均支持。具体同轮原生投递/进程关闭须在实现任务中真实验证，发现基础缺口时只修已有 HAPI 路径并更新固定版本，不新增执行框架。

SDK 工具响应是已验证结果入口，没有可靠的宿主后台唤醒。普通报告缺少结构化格式不抹掉原生结果。模型参数真实验收选择当前原生有效配置中的明确 model/effort；此 Change 不维护模型列表。

schema v1→v2 只增加业务表，资源 ID 和现有客户端数据保留；遇到更高版本按原规则报错，不自动删除数据。任务库集中在中心，不散落临时目录。只启动专用测试服务与模型环境，沿既有授权使用原生认证且不修改用户配置。

## 验证路径

先用真实 SQLite 和 HAPI HTTP fixture 验证接受、身份、断线/崩溃窗口及单轮停止；再验证串行下一轮、resume 精确缺失重建、迟到中断、默认审批与实际原生追加。最后用两种原生 MCP 宿主分别调度两种 runtime，覆盖本地共享非 Git、CLI 控制、断线后收尾、结果分页和重复请求，并实际检查受控子进程退出及 CLI 再委派拒绝。编译 CLI、候选包安装及原有回归通过后同步 Specs/归档，真实远端能力不在本 Change 冒充验收。
