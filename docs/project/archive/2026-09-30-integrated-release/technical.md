# 完整发行技术方案

> 来源：[Requirement](requirement.md)、[Research](research.md)
> 状态：已确认
> 更新：2026-09-30

## 就绪性

以既有单 CLI、固定 HAPI、统一数据根和已实现协作接口做发行整合，不新增执行层或领域功能。方案按持续授权确认；2026-09-30 用户明确允许 Playwright，并接手 macOS 实机验证，环境阻塞解除。实施前完成 C11 看板验收；本 Change 的 Plan 已完成一次 iclaude 评审，采纳记录见 Execution。

## 发行产物

首个完整发行使用 1.0.0，与阶段候选 0.1.0 区分；沿主 npm 包与 macOS/Linux arm64/x64 四平台包。源码开发工程继续 private，生成包移除 private:true；包描述与用户入口文档改为已验收的完整能力，未公开发布的事实保持明确。`package` 只构建并打包，不调用 npm publish、push 或创建 PR。

每个平台继续提供相邻 Runweft/HAPI 程序、HAPI 许可/NOTICE/工具许可及匹配源码归档；固定 HAPI revision 与二进制 hash 的现有核对继续生效。安装不需要开发源码或全局 Bun，MCP 只配置 Runweft 命令。未发布时可从平台 tarball 解包并直接运行 bin/runweft；常规 npm 安装仍需同时提供主包与平台依赖的 registry，不要求用户另装 HAPI。

在既有包 index 中记录 root 源码 revision、工作区是否有改动、配套 HAPI pin、平台程序 SHA-256 和 tarball SHA-512，另输出十六进制 SHA256SUMS，形成一个版本证据入口。先保存 C11 最终 0.1.0 包和索引，再用独立暂存目录构建新版本，成功后替换交付目录，避免旧 tarball 混入。T1 完成提交后从固定代码构建最终矩阵候选；证据保存同一程序 hash。验收期间若改产品代码，重新构建并重跑受影响组合；仅包内说明变化时重新打包和安装验证，程序 hash 一致的模型证据可复用。

## 源码、部署与升级

干净源码顺序为 submodule 初始化、root/HAPI frozen install、类型/根测试、配套构建和发行包。CI build job 在 types/tests 前安装 HAPI 工作区依赖，平台 install jobs 安装 smoke 所需 root 依赖；沿已有四平台 jobs，不新增有权访问模型凭据的公共 CI 流程。Linux x64 实测安装与服务；arm64 构建并探查可执行的本地仿真环境，证据区分仿真、原生与仅格式检查。

README 与使用说明统一入口：获取程序、init/start、MCP 全局安装、机器登记、runtime 登记与 Agent 定义各自独立，再进入共享/本地 worktree/远端工作区协作和看板。保留可复制配置、有效值与路径说明；删除已交付能力仍列为“后续”的过时描述。

发行整合不改变 schema v6。升级试验从已验证的 0.1.0 程序写入的专用数据副本开始，确认 1.0.0 能报告仍运行的旧版本并要求重启，再停服务、备份业务库/HAPI 数据/文件与必要源仓库，保留身份、任务、refs 和原生配置后升级并恢复查询。回退试验再包含新程序产生的数据。更高 schema 的现有拒绝不能改成静默降级；用户文档只承诺已验证的 schema v6 兼容边界，未发布的 0.1.0 是实验基线，不是推荐用户安装的历史版本。

## 完整验收组合

| 维度 | 最终证据 |
| --- | --- |
| 安装与全局 MCP | 同一包的真实安装；使用专用配置预置其他 MCP，显式验证连续两次 install、uninstall 后配置保留和 backups/restore，不调用模型；普通输出无秘密 |
| local 与 Hub | 独立配置/数据所有者、带/不带 Runner 的服务、诊断、重启和凭据/任务持久性 |
| 两宿主 × 两 runtime | 已安装候选通过原生 Codex/Claude MCP 发起任务；输入、派生、等待、报告、续接、停止事实与子 MCP 禁用 |
| shared / 本地 worktree / 远端 worktree | 每组合固定候选；collaboration 覆盖共享 8、本地 worktree 8、远端 4 组；附件入口另覆盖本地共享/独立的两宿主与两 runtime，远端组合直接含输入/输出。准备先于启动、实际保留现场与 Git 成果；明确物理跨机未执行 |
| 控制与失败 | 真实审批/中断和停止；未知不重发、准备失败不启动、封存失败保留、交付重试不重跑模型沿领域已验收注入方式，不新建状态机 |
| 原生历史缺失 | 两 runtime 在专用历史为空的原生 home 下，先获得 HAPI 的精确 missing，再由业务重建历史；核对随机记忆、来源 round ID、新原生 ID、原生输入仅一次和停止，不删除原历史；现有编译产品已完成 Research 实测，最终候选沿同一路径验证 |
| 看板与成果 | 当前候选读取上述任务，代码/文件与执行分开、同源登录及真实 HAPI 会话详情；浏览器证据与 HTTP 检查分别归档 |
| macOS | 同版本 arm64/x64 程序与安装包一并构建，检查文件格式、包内容、许可及校验和；实机安装、诊断、MCP 与真实协作由用户验证，交付时提供操作与预期结果，不以交叉编译代替运行证据 |

最终矩阵沿现有 smoke 脚本，补足缺失的组合和真实重建，记录候选 hash、原生版本、宿主/runtime/模式及证据路径。公共 CI 保持无模型；真实原生验收沿专用复制配置和当前机器已有认证，不转存凭据到 GitHub 或其他新服务。

## 依赖与收尾

- 看板：C11 使用用户已授权的 Playwright Chromium，完成信号为实际页面断言、候选安装及 Requirement 映射通过并归档；此 Change 不接手未完成页面。
- Mac：用户负责实机验收，本次交付负责完整双架构产物、安装入口、校验信息和验证说明。不等待 Mac 执行入口，实机验证标为用户待执行。
- 发布：目标为可发布产物，不自动发布。最终交付包、hash、兼容 HAPI、安装/配置入口与证据；实际 push/npm publish 另依明确授权执行。

通过完整矩阵后同步 release/distribution 与 release/acceptance Specs，引用各领域事实，归档本 Change。环境或失败项仍未解决时不能把“编译成功”写成完整交付。
