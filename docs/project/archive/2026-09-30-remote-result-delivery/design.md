# 远端代码回收设计

> 来源：[本 Change 需求](requirement.md)、[跨 Change 架构](https://github.com/iTgo-lyq/runweft/blob/e85ef3af1b9fed9cc9ac00bcd764d3954bb283da/docs/project/architecture.md)
> 按用户要求保留需求阶段方案讨论，不表示 Technical 已确认。
> 已确认：成果可取回、附件集中管理、轮次结束保留 worktree 供续接、独立 worktree 自动 checkpoint 和默认 bundle 交付。具体清理期限、配额及接口细节在正式方案中落实。

## 1. 结果清单

每轮结果关联主体、主工作区、仓库、delegation、round、HAPI 执行身份与初始基线。清单分开记录：

| 内容 | 表达 |
| --- | --- |
| 执行结论 | HAPI 原生成功/失败/中断事实和必要错误；未知不能写成功 |
| 报告 | 原生最终答复；agent 可另提供测试、阻塞和改动说明 |
| Git 成果 | 初始 base、本轮开始 HEAD、成果 head、对象格式、传输对象与校验结果 |
| 附件 | artifactId、内容 hash、长度、名称、类型、用途及可访问状态 |
| 交付情况 | 完整、部分或失败；逐项说明缺少的必需成果 |

Agent 提供的测试结论属于其报告；程序实际运行的检查另记执行证据。Git 校验通过不能被表述成构建或业务验收通过。

## 2. 消费公共 Git 封存结果

Git 收尾由[公共工作区设计](../../archive/2026-09-29-local-workspace-execution/design.md#本轮固定成果)统一定义并实现，本 Change 不再维护另一套自动提交逻辑。HAPI 确认终态和停止写入后，由公共能力按已确认的 checkpoint 策略保存初始 base、本轮开始 HEAD、成果 HEAD 与不可变引用。

远端交付只接受与 delegation/round/环境匹配的有效封存证据。封存失败保留 worktree，不生成“完整交付”；失败或中断执行可交付部分成果，但执行结论不变。报告任务无改动时只交报告；意外改动按公共规则明确列出，不能隐藏。

成果固定后才从不可变引用生成 bundle，下一轮可沿委派规则继续使用 worktree。网络上传可与后续执行并行，但上传失败不得重新生成提交或重新运行 agent。

## 3. 默认 Git 交付方式

默认通过中心存储交付 Git bundle，避免把成果取回依赖于自动向用户仓库推送。Git 引用仍是代码成果身份；bundle 是传输载体，不是普通文件夹压缩包。

- 初始 `baseCommit` 已作为可恢复输入保存；每轮 bundle 建议覆盖从该初始 base 到当前成果 HEAD 的新增可达对象，而不是只依赖上一轮已取回。
- 中心验证内容 hash、长度、bundle 格式、前置 commit、声明结果引用及祖先关系。可在独立 bare 验证仓库中结合基线导入，禁止执行项目脚本或检出并运行代码。
- 校验与持久化完成后才将 Git 成果标为可取回。远端返回 SHA、agent 说已 push 或上传请求已接受都不构成这一证据。
- 输入基线与输出 bundle 的保留关系必须记录；删除基线对象会破坏后续增量结果，不能只按文件各自 TTL 回收。
- Git LFS 产物和子模块提交需要独立可取回来源。未具备相应传输能力时，不得仅凭 Git 主仓库 bundle 宣称完整交付。

成果 HEAD 等于初始 base 时，清单明确记录“没有新增提交”，直接引用已保留基线，不尝试创建空增量 bundle。同一 subagent 后续某轮没有新改动时，保留该轮报告及原成果 HEAD，可复用已经验证的代码传输对象，不制造提交来区分轮次。

已授权的 Git remote 推送可作为另一种交付方式，验证固定成果 SHA 可被调用方读取；不默认创建 PR、推送主分支或合并。PR 是评审协作动作，可由主 agent 或明确授权的子 agent 执行，不能作为所有子任务的强制结果。

## 4. 主工作区取回

`runweft result fetch <resultId>` 的建议行为：

1. 核对当前主体和目标主仓库绑定，下载已发布结果。
2. 在本地验证 bundle 前置对象和成果身份；缺少初始基线时先取回该结果所绑定的基线。
3. 只导入声明的结果引用，例如 `refs/runweft/results/<delegationId>/<roundId>`。同名不同 SHA 拒绝覆盖，相同结果重复取回无副作用。
4. 返回原始 base、成果 head、导入引用与可读 diff 入口。

取回只更新对象库和专用引用，不 checkout、merge、cherry-pick，也不修改当前分支、暂存区或未提交文件。接纳改动由主 agent 的后续明确操作完成；冲突是本地主工作区的合入问题，不能使已经交付的远端成果消失。

**无 push 的合码路径：** 远端 worktree 内先形成 Git 提交，从固定成果引用生成 bundle，经附件通道传回；主仓库用 Git fetch 导入对象和专用成果引用，主 agent 检查 diff 后按任务执行 merge 或 cherry-pick。bundle 保存原提交对象和 SHA，传输不改写历史；合入策略可能产生新的本地主提交。仅返回 SHA 或保留远端目录不足以合码，主仓库必须实际拿到对应对象。

本地独立 worktree 若与主工作区共享同一 Git 对象库，成果分支本就在该仓库内，可直接由主 agent 合入，无需 bundle。远端则必须经过对象传输。两种路径均将“供下一轮使用的工作区”与“本轮固定成果”分开；成果取回或合入不自动删除 worktree。这里解释 Git 原理与建议流程，不表示 Runweft 命令已经实现。

## 5. 附件接口

输入和输出文件复用[任务附件与交付记录](../../archive/2026-09-29-task-artifact-delivery/design.md)，本 Change 不再定义上传、访问控制或配额。它负责在发布 Git 成果前校验 bundle 语义，登记基线与输出对象之间的保留关系，并把 Git 校验结论组合进每轮结果清单。

## 6. 发布与交付确认

一个 result 只有在全部必需内容持久化并校验后才能发布为完整。可先发布报告或部分成果，但必须逐项暴露未交付项；同一轮的补交建立新清单版本，不能悄悄改写已经引用的内容。

网络失败时重试同一个上传或发布请求，结果清单按稳定身份去重；不重新执行 agent。中心已经收下结果但回执丢失时查询发布记录，不能再次生成不同 checkpoint 来“重试”。

父任务离线时中心保留成果。取回确认仅表示某主体已经取得结果，不代表用户验收，也不自动合并代码或删除远端环境。

## 7. 工作区关闭与清理

自然结束一轮关闭子执行进程，但保留 delegation、worktree 和 session 依据供追加任务。显式关闭协作上下文后，需同时满足以下条件才能自动清理远端环境：没有活跃/未知执行、没有未封存改动、所有要求保留的成果已持久化、没有待完成上传或恢复操作。

中心成果与远端工作树分别设置保留策略。建议未取回、失败待恢复及被引用的结果保持固定，不因普通缓存 TTL 被删除；空间压力触发暂停新任务和清理提示。具体保留期限与配额应在部署配置中明确，不能以无限保存掩盖容量问题。

普通关闭只标记可回收，不清空用户仓库。删除未回收成果是单独的显式操作，提示损失范围；已有结果失效时返回明确的已过期/已删除状态，不持续展示可取回。
